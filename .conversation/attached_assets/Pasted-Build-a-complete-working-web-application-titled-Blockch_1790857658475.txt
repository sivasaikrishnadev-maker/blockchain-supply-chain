# 2. PROJECT PURPOSE

The application tracks a product as it moves through:

Manufacturer
↓
Distributor
↓
Retailer
↓
Customer

The system records important supply-chain events and stores a cryptographic product hash on the blockchain.

The customer can enter a Product ID or scan a QR code to see:

- Product information
- Current supply-chain status
- Supply-chain timeline
- Blockchain transaction information
- Integrity verification result

The blockchain should be presented as a tamper-evident record of the application's stored supply-chain information.

Do NOT claim that blockchain physically proves that a real-world product is genuine.

# 13. BLOCKCHAIN WORKFLOW

When the manufacturer creates a product:

Product data
↓
Generate SHA-256 hash
↓
Save product in MongoDB
↓
Register product hash on blockchain
↓
Save blockchain transaction hash in MongoDB

When a supply-chain event occurs:

Event data
↓
Generate hash
↓
Store event in MongoDB
↓
Record event on blockchain
↓
Save blockchain transaction hash

Use environment variables for blockchain configuration.

Never hard-code private keys.

Create:

.env.example

with:

MONGODB_URI=
JWT_SECRET=
BLOCKCHAIN_RPC_URL=
PRIVATE_KEY=
CONTRACT_ADDRESS=

Do NOT commit real private keys or secrets.

# 14. PRODUCT HASH / INTEGRITY VERIFICATION

Create a function that generates a deterministic SHA-256 hash from the important product fields.

When verifying:

1. Retrieve the product from MongoDB.
2. Recalculate the current product hash.
3. Retrieve the original blockchain hash.
4. Compare them.

If they match:

"Record Integrity Verified"

If they do not match:

"Record Has Been Modified"

Clearly explain in the UI:

"Blockchain verification confirms that the stored record matches the blockchain record. It does not independently verify the physical product."
